## 摘要

**问题**：专业营养师费用高、预约难，普通人无法获得个性化饮食指导。卡路里记账类 App 又只能"记"，不能"看、算、建议、生成、互动"。

**方案**：本项目构建一个 **AI 驱动、带社交互动的私人营养师系统**。它能"看"（多模态 LLM 识别食物）、"算"（每日营养聚合与缺口分析）、"建议"（基于《中国居民膳食指南》的 RAG 检索 + 安全拦截）、"生成"（按目标/预算/忌口生成一日三餐 + 购物清单）、"互动"（记录可设公开，广场点赞 + 评论分楼）。

**技术栈**：Java **SpringBoot**（主业务）+ Python **FastAPI**（AI 微服务）+ **Vue3 + Element Plus + ECharts**（前端）+ **MySQL/H2**（数据持久化），多模态 LLM 通过 API 调用，不训练模型。

**成果**：
- 完整跑通「注册登录 → 拍照/文字录入 → AI 识别 → 手动修正 → 每日报告 → 缺口提示 → RAG 建议 → 菜谱生成 → 公开 → 点赞 → 评论分楼」全流程。
- 实现 7 大模块、36 个测试用例，主链路通过率 100%。
- 4 人协作，2 周周期，代码 + 文档完整交付，Gitee 分支管理规范。

**关键词**：AI 营养师；多模态识别；RAG；菜谱生成；社交互动；SpringBoot + FastAPI 混合架构

### 讲解要点
> 30 秒版："我们做了一个 AI 营养师 App，不是记账工具，而是能看、能算、能建议、能生成、还能和社区互动的私人营养师。技术上是 SpringBoot + Python 双服务 + Vue3，2 周 4 人完成。"

## 一、绪论

### 1.1 研究背景

随着生活节奏加快与饮食结构变化，减脂、增肌、控糖/三高人群规模持续扩大；与此同时，专业营养师资源稀缺（费用 200-500 元/小时、需提前数日预约），**绝大多数普通人无法持续获得专业指导**。

现有产品分两类：
- **卡路里记账 App**（薄荷、MyFitnessPal）：解决"记"，但营养数据靠人工查表，工作量大、易放弃。
- **AI 拍照识别**（如部分大厂 Demo）：能"看"，但给不出依据、不会考虑个体差异、不能形成社区。

我们发现一个**空白**：**让普通人拥有一个"会看、会算、会建议、会生成、能互动"的 AI 营养师**。它应该：
- 像专业营养师一样"懂你"（基于用户画像）
- 像家庭医生一样"有据可依"（基于权威膳食指南 RAG）
- 像朋友圈一样"有反馈"（公开记录 + 点赞评论）

### 1.2 国内外研究现状

| 类别 | 代表产品 | 优点 | 不足 |
|---|---|---|---|
| 传统记账 | 薄荷健康、MyFitnessPal | 数据全、社区活跃 | 手动输入繁琐，无 AI 识别 |
| AI 识别 | B 站美食 AI、各大厂 Demo | 拍照即得营养 | 单次识别，无后续建议 |
| 营养社区 | 小红书、微博 | 互动好 | 营养内容零散、无个性化 |
| 专业营养师服务 | 薄荷营养师、Keep 私教 | 专业 | 贵、难约、不持续 |

**机会点**：将"AI 识别 + RAG 建议 + 菜谱生成 + 社交互动"整合为**闭环产品**，弥补"工具 → 服务 → 社区"的鸿沟。

### 1.3 项目意义

1. **实用价值**：让月薪 5000 也能用上"营养师"，填补"想吃健康但没人教"的市场空白。
2. **技术价值**：探索"RAG + 多模态 LLM + 微服务"在 ToC 健康场景的落地范式。
3. **工程价值**：2 周 4 人从 0 到 1 全栈交付，验证**模块化分工 + 严格分支管理 + 文档同步**的高效协作模式。

## 三、系统设计

### 3.1 总体架构

```
                    ┌─────────────────────────┐
                    │   浏览器 Vue3 + Element  │
                    │      localhost:5173      │
                    └────────┬───────┬────────┘
                     /api/*  │       │  /ai/*        ← Vite 开发代理
                             ▼       ▼
        ┌────────────────────────┐  ┌──────────────────────────┐
        │  SpringBoot 主服务      │  │  FastAPI AI 微服务        │
        │     localhost:8080     │  │      localhost:8000      │
        │  用户/记录/报告/社交     │  │  识别/建议/菜谱/安全       │
        └───────────┬────────────┘  └──────────┬───────────────┘
                    │                          │
                    ▼                          ▼
              ┌───────────┐            ┌──────────────┐
              │   MySQL   │            │  LLM API     │
              │  (可选)    │            │ (可不配置)     │
              └───────────┘            └──────────────┘
```

**关键设计决策**：

1. **前后端分离 + 双后端**：浏览器只跟 Vite Dev Server 通信，业务接口走 8080，AI 接口走 8000。Vite 代理在开发期将 `/api/*` 和 `/ai/*` 转发到对应后端。
2. **AI 独立为 Python 微服务**：SpringBoot 调多模态/向量库生态弱；Python（FastAPI）调 LLM、LangChain、向量库最顺。两服务是**并列**关系，前端直接调 AI，不走 SpringBoot 转发。
3. **数据库默认 H2 内存库**：零配置启动即跑；切 MySQL 只需 `-Dspring-boot.run.profiles=mysql`。
4. **AI 失败可降级**：未配 LLM Key 时，本地规则/模板仍能跑通，答辩不被网络问题卡住。

### 3.2 技术选型理由

| 技术 | 用途 | 选择理由 |
|---|---|---|
| **SpringBoot 2.7** | 主业务 | 企业级主力框架，JPA 自动建表，Spring Security 支持 JWT 成熟 |
| **FastAPI** | AI 微服务 | Python 异步、原生 OpenAPI 文档、Pydantic 校验、调 LLM/向量库最顺 |
| **Vue 3 + Vite 6** | 前端 | Composition API 写状态清晰；Vite 启动 < 1s，HMR 流畅 |
| **Element Plus** | UI 组件库 | 中后台风格齐全，省去自研组件时间 |
| **ECharts 5** | 图表 | 一周趋势、缺口可视化开箱即用 |
| **MySQL 8 / H2** | 数据库 | MySQL 持久化；H2 内存库零配置 |
| **JWT (jjwt 0.11)** | 鉴权 | 无状态，跨域友好，适合前后端分离 |
| **多模态 LLM (gpt-4o-mini 等)** | 识别 + 生成 | 通过 API 调用，不训练模型；支持图片 + JSON 输出 |
| **本地关键词检索** | RAG 简化 | 受限于 2 周周期，未接向量库；用膳食指南条目 + 关键词打分替代 |

### 3.3 数据库设计

#### 3.3.1 ER 概览

```
user 1──N food_record 1──N comment
                │
                ├──N like
                │
                └──N nutrition_daily（按天聚合）
```

- 一个用户多条记录
- 一条记录多个点赞、评论
- 评论支持两层（一级 + 回复）
- 每日聚合按 (user, date) 唯一

#### 3.3.2 核心表

| 表 | 关键字段 | 索引 | 说明 |
|---|---|---|---|
| `user` | id, username(UNIQUE), password(BCrypt), height, weight, age, gender, goal, avoid, allergy | idx_username | 用户 |
| `food_record` | id, user_id, food_name, portion, meal_type, calories, protein, fat, carbs, fiber, sodium, image_url, confidence, is_corrected, visibility(public/private), record_date | idx_user_date, idx_visibility | 饮食记录 |
| `nutrition_daily` | id, user_id, record_date, total_* | uk_user_date | 每日聚合（用于快速出报告） |
| `like` | id, user_id, record_id | uk_user_record, idx_record | 点赞（uk 防重） |
| `comment` | id, record_id, user_id, parent_id, content | idx_record, idx_parent | 评论（parent_id 自关联，支持两级分楼） |
| `ai_log` | id, user_id, type, latency, success | idx_user_type | AI 调用日志（可选） |

#### 3.3.3 关键设计

- **点赞防重**：`uk_user_record(user_id, record_id)` 唯一索引，重复点赞直接抛 `DuplicateKeyException`，前端 catch 后不计数。
- **评论分楼**：`parent_id` 自关联，0 = 一级评论，>0 = 二级回复；查询时按 `(parent_id, created_at)` 排序即可。
- **公开广场性能**：`idx_visibility(visibility, created_at)` 联合索引，分页查询 "where visibility='public' order by created_at desc" 走索引。
- **JPA 自动建表**：开发期 `spring.jpa.hibernate.ddl-auto=update`，首次启动按 Entity 自动建表；生产期切 `validate`。
- **H2 内存库**：默认 profile 下，演示账号通过 `DemoDataInitializer`（`CommandLineRunner`）在启动时初始化，重启数据清空。

> 完整 SQL 见 `doc/sql.md` 第三节。

|---|---|---|---|

#### 3.4.3 统一响应

```json
{ "code": 0, "msg": "ok", "data": { ... } }
```

- `code=0` 成功；`code=401` 未登录；`code=403` 无权限；`code=400` 参数错；`code=500` 服务异常。
- JWT 拦截器 `AuthInterceptor` 解析 `Authorization: Bearer <token>`，将 userId 写入 `UserContext`（ThreadLocal）。
- 拦截器白名单：`/api/user/register`、`/api/user/login`。

### 4.2 关键算法 1：基础代谢与目标摄入

```java
// NutritionCalculator.java
public static double bmr(User u) {
    double w = u.getWeight(), h = u.getHeight(), a = u.getAge();
    return u.getGender().equals("男")
        ? 10*w + 6.25*h - 5*a + 5
        : 10*w + 6.25*h - 5*a - 161;
}

public static double targetCalories(User u) {
    double b = bmr(u);
    return switch (u.getGoal()) {
        case "减脂" -> b * 1.2 - 500;
        case "增肌" -> b * 1.5 + 300;
        default     -> b * 1.3;   // 维持 / 控糖
    };
}
```

- **Mifflin-St Jeor 公式**（行业标准）
- 三类目标用经验系数：减脂 1.2×-500 kcal，增肌 1.5×+300 kcal，维持 1.3×
- 实测：demo 用户 175cm/75kg/22 岁男 → BMR ≈ 1750，目标减脂 ≈ 1600 kcal

### 4.3 关键算法 2：每日缺口

```java
double gap = targetCalories(user) - sumCalories(records);
double proteinGap = targetProtein(user) - sumProtein(records);
// ... 脂肪、碳水、纤维、钠同理
```

- 正数 = 缺口（需要补充）；负数 = 超标（需要减少）
- 前端用红/绿配色直接展示，零额外计算开销

### 4.4 关键算法 3：点赞 toggle（防重）

```java
// LikeServiceImpl.java
public LikeResult toggle(Long recordId) {
    Long userId = UserContext.require();           // 1. 鉴权
    FoodRecord r = recordRepo.findById(recordId)
        .orElseThrow(() -> new BizException("记录不存在"));
    if ("private".equals(r.getVisibility()))
        throw new BizException("私密记录不可赞");

    Optional<Like> exist = likeRepo.findByUserIdAndRecordId(userId, recordId);
    if (exist.isPresent()) {
        likeRepo.delete(exist.get());              // 2. 取消点赞
        return new LikeResult(false, likeRepo.countByRecordId(recordId));
    }
    likeRepo.save(new Like(userId, recordId));     // 3. 新增点赞
    return new LikeResult(true, likeRepo.countByRecordId(recordId));
}
```

**防重机制**：依赖 `uk_user_record` 唯一索引。即使前端被绕过，DB 层也会抛 `DuplicateKeyException`。
**计数**：用 `countByRecordId` 实时查询（数据量小，< 1ms；后续可加 Redis 缓存）。

### 4.5 关键算法 4：评论分楼

```java
// CommentServiceImpl.java
public Comment add(Long recordId, Long parentId, String content) {
    if (parentId != null) {
        Comment parent = commentRepo.findById(parentId)
            .orElseThrow(() -> new BizException("父评论不存在"));
        if (parent.getParentId() != null)
            throw new BizException("不允许回复二级评论");   // 最多两层
    }
    // ... 保存
}
```

**展示**（前端组装）：
```js
const top = comments.filter(c => c.parentId === null)
                     .sort((a,b) => b.createdAt - a.createdAt)  // 倒序
for (const t of top) {
  t.replies = comments.filter(c => c.parentId === t.id)
                      .sort((a,b) => a.createdAt - b.createdAt) // 正序
}
```

**级联删除**：删一级评论时，DB 设 `ON DELETE CASCADE` 或后端先查回复再删（实测用后端逻辑删除，便于审计）。

### 4.6 关键算法 5：JWT 鉴权链

```
请求 → AuthInterceptor.preHandle
  → 从 Header 拿 "Authorization: Bearer xxx"
  → JwtUtil.parse → userId
  → UserContext.set(userId)（ThreadLocal）
  → return true（白名单直接放行）

请求结束 → afterCompletion
  → UserContext.clear()（防内存泄漏）
```

```java
// AuthInterceptor.java
if (request.getRequestURI().matches("/api/user/(register|login)")) return true;
String auth = request.getHeader("Authorization");
Long userId = JwtUtil.parse(auth.replace("Bearer ", ""));
UserContext.set(userId);
return true;
```

**白名单注册**：`WebConfig.addInterceptors(...).excludePathPatterns("/api/user/register", "/api/user/login", "/h2-console/**", "/error")`。
**前端配合**：`axios request.js` 拦截器自动从 `useUserStore` 取 token 塞 header；响应 401 时清 token 跳登录。

### 讲解要点
> 3 分钟版：选 2-3 个算法讲（BMR/缺口是基础、点赞防重/评论分楼是亮点）。每个算法先讲"为什么这么做"（业务诉求）→ 再讲"具体怎么做"（代码片段）→ 最后讲"边界情况"（异常分支）。JWT 链讲一次就够，不用太深入。

## 五、AI 子系统设计

> 本章是项目**最具差异化**的部分，讲好能多拿 5-10 分。

### 5.1 多模态食物识别

**输入**：Base64 图片 或 文字描述  
**输出**：`{foods: [{name, portion, calories, protein, fat, carbs, fiber, sodium, confidence}]}`

**Prompt 模板**（节选）：

```
你是一位专业营养师。请识别图片/描述中的所有食物，估算份量和营养。
严格输出 JSON，格式：
{
  "foods": [
    {"name": "牛肉面", "portion": "一碗 约300g", "calories": 450,
     "protein": 20, "fat": 15, "carbs": 60, "fiber": 3, "sodium": 1200,
     "confidence": 0.85}
  ]
}
如果不确定，confidence < 0.6 并给出备选。
```

**降级策略**：未配 LLM Key 时，本地规则按"食物名 → 查表 → 返回固定营养值"返回，confidence=0.5，提示用户修正。

### 5.2 RAG 营养建议（核心）

**问题**：LLM 可能"一本正经地胡说"，给错误饮食建议有健康风险。  
**方案**：RAG（检索增强生成）——**先从膳食指南检索相关内容，再让 LLM 基于检索结果生成建议**。

**流程**：
```
用户缺口（热量 -600、蛋白质 -40）
    ↓
RAG 检索：关键词匹配 10 条膳食指南条目
    ↓ 命中 3 条：
    - "减脂期蛋白质摄入 1.2-1.6g/kg"
    - "晚餐推荐高蛋白低脂，如鸡胸肉、鱼"
    - "每日钠摄入 < 2300mg"
    ↓
Prompt 拼接：
"你是营养师。用户目标：减脂。今日缺口：热量 -600、蛋白质 -40。
 参考以下指南：{检索到的 3 条}。请给具体可执行的下一餐建议。"
    ↓
LLM 输出："晚餐建议：清蒸鸡胸肉 150g + 西兰花 200g + 糙米饭 80g...",
"依据：减脂期蛋白质 1.2-1.6g/kg、晚餐高蛋白原则"
```

**简化版（本地）**：用 10 条硬编码指南条目 + 关键词打分排序，未接向量库；LLM 模式用真实 prompt。
**免责声明**：所有建议末尾追加"以上建议仅供参考，不替代专业医师诊断"。

### 5.3 安全拦截

**触发时机**：建议生成后、返回前端前。  
**规则**（依次检查，遇阻即返回）：

| 规则 | 阈值 | 拦截消息 |
|---|---|---|
| 热量低于基础代谢 | `advice.calories < user.bmr` | "建议热量过低，可能影响基础代谢" |
| 极端节食 | `advice.calories < 800` | "建议热量极低，不可持续" |
| 违禁药物关键词 | 关键词匹配 "减肥药"、"利尿剂"等 | "建议涉及违禁内容" |
| 过敏原冲突 | 建议含 `user.allergy` | "建议含你的过敏原（X）" |

**实现**：`/ai/safety-check` 独立接口，可被前端单独调用（先验、后渲染）。

### 5.4 菜谱生成

**输入**：`{goal: 减脂, budget: 50, ingredients: 鸡蛋/西兰花, avoid: 香菜}`  
**输出**：

```json
{
  "breakfast": {"name": "燕麦鸡蛋粥", "ingredients": [...], "calories": 350, "protein": 18},
  "lunch":     {"name": "鸡胸肉沙拉", ...},
  "dinner":    {"name": "清蒸鱼+西兰花", ...},
  "shoppingList": ["燕麦", "鸡蛋", "鸡胸肉", "西兰花", "鲈鱼", ...]
}
```

**Prompt 要点**：
- 明确"中餐习惯、口味清淡、家常食材"
- 预算约束（"三餐合计 < 50 元"）
- 忌口硬约束（"绝对不出现 {avoid} 中任何一项"）
- 购物清单要去重合并（如早/午餐都用了鸡蛋，列 1 个总数）

### 5.5 AI 失败降级总表

| 场景 | 降级方案 |
|---|---|
| 未配 LLM Key | 本地规则/模板返回 |
| API 超时 | 返回提示"AI 暂时不可用，请稍后重试" |
| 识别失败 | 前端允许"手动输入" |
| 建议被拦截 | 前端红色横幅展示拦截原因 |

### 讲解要点
> 3 分钟版：把"会看 → 会算 → 会建议 → 会生成 → 安全"画成一条线讲。重点讲 RAG（"建议有依据、不让 LLM 自由发挥"）和安全拦截（"健康场景不能出错"）两点。可用真实截图展示建议 + 依据。

## 附录 A：营养计算公式

```
BMR (Mifflin-St Jeor)：
  男：10×体重(kg) + 6.25×身高(cm) - 5×年龄 + 5
  女：10×体重(kg) + 6.25×身高(cm) - 5×年龄 - 161

目标摄入：
  减脂：BMR × 1.2 - 500 kcal
  增肌：BMR × 1.5 + 300 kcal
  维持：BMR × 1.3
  控糖：BMR × 1.3（碳水 < 总热量 45%）

营养素推荐（成人）：
  蛋白质：0.8-1.2 g/kg（减脂期 1.2-1.6）

  碳水：总热量 45-65%（控糖 < 45%）
  钠：< 2300 mg/天
  纤维：25-30 g/天
```
